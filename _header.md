# Automation Account

Deploys an Automation Account and its optional automation resources and private endpoints.

The module and its examples use AzAPI for Azure control-plane resources. Terraform 1.11 or later and `Azure/azapi ~> 2.12` are required. AzureRM is no longer a module dependency.

This is the provider migration delivery. Child resources retain their existing root collection boundaries; extraction into the local submodules required by TFRMNFR1 is a separate, deferred migration. Do not interpret passing static or mocked checks as proof of full structural compliance or compatibility with applied AzureRM state.

## Consumer upgrade changes

- Use `parent_id` for the existing resource group's ARM ID and the typed `sku` object. Outputs use `resource_id` and `name` rather than the old `automation_account_id` and `automation_account_name`.
- Standard private endpoint, diagnostic, identity, lock, role-assignment and CMK inputs follow their current typed interfaces. Review the generated input descriptions before upgrading; legacy object attributes are not automatically translated.
- `resource_types` and `ignore_body_changes` use deterministic ARM-derived keys. Body-ignore paths are body-relative dot notation, are not sent to Azure, and changes take effect after apply.
- Back up state and inspect every provider move against the actual resource IDs. Require zero unintended destroys or replacements and an empty second plan. Real-state upgrade and Azure deployment validation are still required.

## Runbooks and schedules

Optional `draft`, content links, hashes and draft parameters may be omitted. Draft parameter objects use their declared `key`, not their list index.

Use `publish_content_link` for published runbooks. A `draft.content_link` with `edit_mode_enabled = false` is published through an AzAPI action after the runbook exists; job schedules and webhooks wait for that publication. Inline `content` is rejected explicitly: AzAPI resource actions do not accept a raw string request body for Automation's text/plain draft-content API ([provider limitation](https://github.com/Azure/terraform-provider-azapi/issues/507)). Host the script at a content-link URI instead of expecting inline content to be silently deployed.

Schedules without `start_time` use a persistent creation timestamp plus seven minutes, avoiding a continually changing timestamp. When upgrading an existing schedule, configure its existing `start_time` explicitly to avoid resetting it. `OneTime` schedules omit `interval`; per-resource timeouts override module-level timeouts.

## Secret payloads and webhook URIs

Certificate contents, credential passwords, source-control tokens and webhook URIs are sent through AzAPI write-only `sensitive_body`, not the ordinary persisted request body. Increment the relevant positive-integer `base64_version`, `password_version`, `security_token_version` or `uri_version` whenever its payload changes. Defaults are 1; changing only a secret without changing its version does not request a rotation.

Encrypted Automation variables also use write-only request values; increment their `value_version` when changing the value. Unencrypted values remain in ordinary provider state. DateTime serialization still uses `time_static`, which retains its timestamp in state even when the Azure variable is encrypted. Likewise, example VM passwords are generated by `random_password`, whose result remains in protected state even though the VM request uses a write-only body.

Supply the existing `uri` when migrating a webhook. When omitted, Azure generates one and the module exposes it through the sensitive `automation_webhook_uris` output. Increasing `uri_version` recreates the webhook and requests a new URI when generated; changing its expiry time also recreates it. Assess downstream consumers before either change. Generated URIs necessarily remain in sensitive provider state and outputs: protect the backend and never publish state or plan files.

The source-control example requires `TF_VAR_security_token` to be configured securely outside the repository and chat. Policy planning and deployments cannot validate this scenario without that input.

## Automation connection migration

Automation connections now use AzAPI. Each `automation_connections` entry manages one ARM connection. The optional `automation_connection_certificates`, `automation_connection_service_principals`, and `automation_connection_classic_certificates` maps supply fields to that connection through `connection_key`; they no longer create separate Terraform resources. At most one specialized entry may reference a connection, and its type must match. Specialized fields override matching `values` entries.

Back up state before upgrading. The module moves `azurerm_automation_connection.this` to `azapi_resource.automation_account_connections`, preserving the input keys when provider state conversion succeeds. Legacy specialized state entries are forgotten without deleting their Azure objects, because they referred to the same connections. Verify that every specialized state entry has the same ARM ID as its corresponding generic entry **before applying**. If the generic entry is missing or IDs differ, stop and reconcile/import the actual connection into the new address rather than applying the automatic migration.

For example, after resolving any duplicate legacy state entries, import a connection missing from the generic state using its actual ARM ID (add the consuming module prefix to the address when applicable):

```powershell
terraform import 'azapi_resource.automation_account_connections["example"]' '/subscriptions/<subscription-id>/resourceGroups/<resource-group>/providers/Microsoft.Automation/automationAccounts/<account>/connections/<connection>'
```

Require a plan with no unintended destroys or replacements, apply, and check that a second plan is empty. The upgrade must be verified against real state; mocked tests do not establish state-conversion compatibility. Connections remain at their existing module boundary during this provider migration; extraction to the local submodule required by TFRMNFR1 is deferred to a separate migration.

Private endpoint IP configurations accept a per-IP `member_name`, falling back to the endpoint's `subresource_name`. Optional endpoint locks and role assignments are implemented with AzAPI in either DNS-management mode. Endpoint role assignments do not perform an Azure Active Directory lookup, so `skip_service_principal_aad_check` is retained for the common interface but has no effect.

## Job schedule migration

Both `automation_job_schedules` and inline `automation_runbooks[*].job_schedule` entries now manage `Microsoft.Automation/automationAccounts/jobSchedules` with AzAPI. Runbooks and schedules also use AzAPI. Job schedules remain at the root module boundary; the local submodule required by TFRMNFR1 is deferred to a separate migration.

Standalone resource keys are unchanged. Inline resource keys are `jsonencode(["runbook", runbook_key, schedule_key])`, so reordering inline entries does not recreate associations. Do not declare the same runbook/schedule pair twice across the two inputs. Job schedules inherit per-job timeouts, then per-runbook timeouts for inline entries, then module-level timeouts. `run_on` selects the Hybrid Worker Group, and parameter names must remain lowercase.

**Before upgrading an existing deployment:**

1. Back up state securely. Read each standalone resource's `job_schedule_id` or `resource_manager_id`, and each runbook's nested `job_schedule[*].job_schedule_id`, from the old state. Match entries by runbook and schedule name, not set/list position.
2. Set `job_schedule_id` to the existing GUID on every association being migrated, including inline entries. Keep these values configured after migration. Omit the field only for genuinely new associations.
3. Plan the upgrade. Declarative import blocks adopt each supplied GUID at the new AzAPI address. The old standalone state entries are forgotten with `destroy = false`; Azure associations are not deleted. Nested legacy runbook associations have no independent Terraform address, so map their existing GUIDs to the new inline entries before moving the runbook.
4. Require no unintended creates, destroys, or replacements of job schedules. Apply the migration, then require an empty second plan. Verify real state before claiming migration success; mocked tests do not prove an Azure upgrade path.

There is deliberately no `moved` block for these associations. Nested blocks are not independent Terraform addresses. Standalone AzureRM job schedules also use a composite Terraform ID (schedule ID plus runbook ID), which AzAPI 2.12 does not translate to the job schedule's ARM ID during cross-provider moves. Use the actual GUID with import instead.

For example, migrate a standalone entry by adding its existing GUID:

```hcl
automation_job_schedules = {
  nightly = {
    job_schedule_id = "11111111-1111-1111-1111-111111111111"
    runbook_key     = "cleanup"
    schedule_key    = "nightly"
  }
}
```

New associations receive a deterministic GUID derived from the account ID and Terraform map key. Retain the same keys to retain those IDs. The referenced runbook must be published through a supported content link or already published in Azure before it can be linked to a schedule. Runbook updates can also regenerate job schedule GUIDs; inspect and reconcile those associations before applying subsequent changes.
